# 流浪地球 · The Wandering Earth

A **Minecraft 1.21.1 / NeoForge** content mod themed around *The Wandering Earth*
(《流浪地球》, films 2019 & 2023 and the novella), designed as a
**Create / Create Aeronautics addon**.

> "道路千万条，安全第一条；行车不规范，亲人两泪流。"
> — 北京第三区交通委

### Working planetary engines

Twelve engine blocks are not decoration — they have real state, a block entity
and a client-side flame effect:

| Feature | How it works |
|---|---|
| **Turns** | `facing` property (4 directions). Place it and it faces you; **sneak + empty-hand right-click** rotates the nozzle a quarter turn, and the blockstate/model follows (per-facing `y` rotation). |
| **Burns fuel** | A `BlockEntity` (`ModEngineBlockEntity`) stores fuel in NBT (`Fuel` / `BurnTimer`). One lighter stone burns for **400 ticks (20 s)**; while burning it keeps `lit=true`, which swaps in the brighter `_front_lit` model. When fuel runs out the engine extinguishes itself. |
| **Needs redstone** | Loading a lighter is not enough: the engine only fires while it receives a **redstone signal** (direct neighbour signal, or a remote link pushed by a Control Panel). Without a signal it sits loaded and cold, which is what makes the panels worth building. |
| **Fires a beacon beam** | A **block entity renderer** (`EngineBeamRenderer`) draws one straight, steady shaft of light out of the nozzle along `facing`, up to `BEAM_LENGTH = 32` blocks and stopping at the first solid block. It uses the vanilla **beacon beam** shader (`RenderType.beaconBeam` + `textures/entity/beacon_beam.png`), so it reads like a lighthouse: a bright core plus a soft halo. The muzzle still emits `SMALL_FLAME` and hums with `BEACON_AMBIENT`. |
| **Loads lighter stones itself** | Right-click with a **Lighter Stone** to insert one. Separately, every second the engine scans a 3-block box for dropped `ItemEntity` lighter stones and pulls them in automatically. |
| **Control Panel** | `engine_control_panel` is a machine block with its own `BlockEntity`. It scans a **8 / 16 / 32 block radius** for engines (sneak + right-click cycles the radius), remembers up to 256 of them in NBT, and pushes its own redstone state to all of them — so one lever fires a whole engine farm. |
| **Ponder** | With Create installed, `com.wanderingearth.compat.WanderingEarthPonder` registers three Create **Ponder** scenes (hold **W** over the item to open the animated explanation). It is loaded reflectively, so the mod still works, with zero `net.createmod.*` references, when Create is absent. |

The other interactive blocks keep their flavour lines: the **undercity lottery**,
the **countdown display**, **MOSS**, the **traffic notice**, the **UEG alert**
and Zhou's **ignition button**. `engine_control_panel` is fully mechanical: it
scans 8/16/32 blocks for engines, stores up to 256 of them in NBT, and pushes
its own redstone state to all of them, so one lever fires a whole array.

Each Ponder scene is backed by a real structure file
(`assets/wandering_earth/ponder/<scene>.nbt`): a 5x5 stone-brick platform with the
machine in the middle, generated by `tools/gen_ponder_schematics.py`. Without it
Ponder logs a load error and animates an empty base plate.

Recipes use **vanilla ingredients only**, so the mod is fully playable
standalone. Optional `create:crushing` / `create:pressing` recipes are also
included and activate when Create is installed. In `neoforge.mods.toml`,
`create` and `aeronautics` are declared as *optional* dependencies so it loads
both with and without them (thematically it is a Create Aeronautics addon).

## Building

Standard ModDevGradle project (Java 21):

```
gradlew build
```

The produced jar is in `build/libs/`. This requires a machine that can reach
`maven.neoforged.net` (ModDevGradle's NeoForm runtime is only published there).
The Gradle wrapper here points at a Tencent mirror for the Gradle distribution.

### Offline build (no maven.neoforged.net)

On networks where `maven.neoforged.net` is unreachable, a full ModDevGradle build
cannot run (NeoForm Runtime `net.neoforged:neoform-runtime:2.0.31` is not
mirrored). This repository therefore also ships an **offline-compiled jar**:
`prebuilt/wandering_earth-1.4.0.jar`. It was produced by compiling the exact
same `src/main/java` sources against the real NeoForge 1.21.1 API jars plus
compile-time-only `net.minecraft.*` signature stubs (verified against Mojang's
official 1.21.1 mappings). The stubs are **not** shipped inside the jar — at
runtime the game supplies the real Minecraft + NeoForge classes. The jar
contains only this mod's classes and resources and installs like any other mod.

See `tools/build_offline.py` for the reproducible offline build, and
`tools/verify_jar.py` for the linkage checker described below.

> **Why the stubs get verified, not just compiled.** A stub that declares the
> wrong *kind* of type (an interface as a `class`, or vice versa) compiles
> perfectly — javac emits `invokevirtual` where the JVM expects
> `invokeinterface` — and then throws
> `IncompatibleClassChangeError` the first time the game touches it. That is
> exactly what broke v1.0.0 (`MutableComponent` was stubbed as an interface;
> it is a class). `tools/verify_jar.py` therefore checks the built jar against
> the real 1.21.1 classes before it is shipped: invoke kinds, member linkage,
> override descriptors, and that no stub leaked into the jar. Run it with:
>
> ```
> python tools/verify_jar.py --jar prebuilt/wandering_earth-1.4.0.jar \
>     --mappings client.txt --vanilla client.jar --cp-dir <neoforge-jars>
> ```
>
> It reproduces the v1.0.0 crash on the old jar and reports 0 problems on this
> one.

## Install

Drop the jar into `mods/` of a Minecraft **1.21.1** + **NeoForge 21.1.x**
instance. Create / Create Aeronautics are optional (recommended, for theme and
the Create recipes).

## The movie map

A hand-generated Minecraft 1.21.1 world that rebuilds the film's four
pillars — planetary engine, undercity, space elevator, surface life — is
built by a small Python generator and kept **on this machine only**. It is
not published on GitHub and is not part of this repository.

Regenerate or edit it locally with the generator in `tools/mapgen/` (pure
standard library: `nbt.py` is a self-contained NBT reader/writer and
`anvil.py` writes the 1.21.1 Anvil format — DataVersion 3955, 24 sections,
packed palette longs, sky/block light arrays). The generator is git-ignored
together with the map, so it stays on this machine:

```
cd tools/mapgen
python build_map.py     # writes map/流浪地球-电影还原
python verify_map.py    # re-reads the save and asserts 47 landmarks + block entities
python render_slices.py # draws top-down / cross-section PNGs into slices/
```

It writes `map/流浪地球-电影还原/` (a `level.dat` + one `region/r.0.0.mca`).
Drop that folder into `.minecraft/saves/`. The engine carries real block
entities, so it loads as a working machine with its fuel state instead of a
plain block.

Layout, the order of the set pieces and the props follow the films;
distances do not.

## Lore notes

Content is based on the films and novella; a few ambiguous items (e.g. the
"singularity data core", "周罗", exact engine counts) are deliberately generic
rather than invented as fact. See `docs/LORE.md`. No copyrighted audio or
original film assets are included — all textures are programmatically generated.

### v1.3.0: the film research pass

1.3.0 is a **fact-checking release**. Every claim in the mod's lore text was
checked against the Chinese and English Wikipedia articles for the two films
and re-checked against what the films actually show; the sources are quoted in
`docs/FILM_LORE.md`, together with a list of the items that are still uncertain
and how the mod treats them.

What changed:

* **Removed claims the films do not support.** The engine is no longer
  described as 11 000 m tall (that number is from the novella), and the
  undercity population is no longer "3.5 billion people" — the films only say
  that **half of humanity** went underground, mostly chosen by **lottery**.
* **Added the numbers the films actually use**: 10 000 planetary engines and
  2 000 turning engines; 3 371 nuclear bombs; 300 astronauts over 50; three
  root servers (Beijing, Tokyo, Dulles) that had to be back online within half
  an hour; 30 000 digits of password; 224 hours until the moon hit Earth; 714
  hours of decryption still needed; the day becoming 60 hours long; the 550A
  running **900+ generations**; the Fire Seed plan being authorised by MOSS
  on its own; the only three 550C machines, one of them lost to a Z9 solar
  storm.
* **New content for the set pieces that had no block yet**: the three lunar
  satellite engines, Sulawesi No.3 turning engine, the lunar phased-array
  bomb rack, the three root servers, the Delhi Digital Life Institute ruins,
  the Ark and Moon-by-Moon terminals, the Fire Seed core, the Emergency Plan
  No.3 display, the Navigator ISS module and control module, the Jining police
  station, the lunar return capsule — plus eight props (Han Zi'ang's vehicle
  card, the Digital Life permit, the bomb placement chart, the root server
  key, the plan manual, Li Yiyi's toolbox, the Fire Seed record, Tu Yaya's
  memory chip).
* Two more engine blocks (the lunar satellite engine and Sulawesi No.3) are
  **real machines**, not decoration: they take lighter stones, need a redstone
  signal and fire a plasma beam like every other engine.

### v1.4.0: the beacon beam

1.4.0 replaces the engine's particle trail with a **real beacon beam**.

The old beam was a trail of `END_ROD` particles emitted from `Block.animateTick`.
That hook is called by the client on **random** blocks only, so the trail
flickered and never stood still — it looked like sparks, not like a beam.

What changed:

* **A block entity renderer draws the shaft.** `EngineBeamRenderer` implements
  `BlockEntityRenderer` and is registered on the **mod** event bus through
  `EntityRenderersEvent.RegisterRenderers` (that event is a mod bus event, so
  it cannot be posted to the game bus).
* **It uses the vanilla beacon shader.** The shaft is drawn with
  `RenderType.beaconBeam(textures/entity/beacon_beam.png, ...)` — the exact
  render type and texture vanilla uses for beacons — as a bright core plus a
  translucent halo, so it blends into the world like a lighthouse.
* **It is frame perfect.** Because the geometry is built every frame instead of
  being sprayed as particles, the beam is perfectly straight and never
  flickers.
* **It comes out of the block, not the camera.** Vertices are written through the
  pose-aware `addVertex(PoseStack.Pose, ...)` overload (the same one vanilla
  `BeaconRenderer` uses), which bakes the block-to-camera translation into each
  vertex. Using the plain `addVertex(float,float,float)` overload would leave the
  shaft at raw camera-space coordinates and make it appear to shoot out of the
  player's viewpoint.
* **It reaches further.** `BEAM_LENGTH` went from 12 to **32** blocks.
* The muzzle still spits `SMALL_FLAME` and now hums with `BEACON_AMBIENT`
  instead of `BLAZE_SHOOT`.

To keep the offline build honest, `tools/build_offline.py` gained
compile-time stubs for the seven client classes this needs (`PoseStack`,
`VertexConsumer`, `RenderType`, `MultiBufferSource`, `OverlayTexture`,
`BlockEntityRenderer`, `BlockEntityRendererProvider`), each carrying the
official 1.21.1 signature including return types, so the compiled descriptors
match the real classes exactly. The real `org.joml` jar is used for
`Quaternionf`. `tools/verify_jar.py` checks the result:

```
invoke sites: 388 | member refs: 445 | fields: 57 | overrides: 19 | phantom types: 0
PROBLEMS: 0
```
